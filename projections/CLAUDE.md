
- **`game_schedule` holds DUPLICATE rows for the same real game under two id namespaces — never COUNT(*) it per team, and never "clean up" the duplicates by deleting one namespace.** The 2025-26 NBA season exists twice in full: an NBA.com-id pass (`0022500002`-style, created 2026-02-22) and a BDL-id pass (`18446820`-style, created 2026-04-28) — 1,232 duplicated games, plus 59 more outside the regular window and 1 WNBA. This made every 2025-26 team look like it played ~166 games, and because the 2026-27 schedule isn't loaded yet, `team_games_per_season`'s recent-season fallback became `PROJECT_GAMES=166` for the whole 2026-27 NBA snapshot — players shipped projected for **98-109 games** (caught by the user in the FA list's "×98 gm", 2026-08-03). Both engine counters ([team_games_per_season and get_team_games_played in projections/franchise_db.py](projections/franchise_db.py)) now use `COUNT(DISTINCT game_date)` per team — a team plays at most one game per date, so date-counting is duplicate-proof; any NEW consumer that derives games-per-team from `game_schedule` must do the same. **The duplicates cannot simply be deleted**: `player_games` 2025-26 is id-format-MIXED (1,112 games logged under NBA.com ids, 120 under BDL ids — no double-logging, but each schedule copy is load-bearing for joins from one slice), and `live_player_stats` is mixed the same way (9,054 vs 6,729 rows). A real cleanup is a remap migration (point the 120 BDL-id `player_games`/`live_player_stats`/`live_scoring_events` slices at their NBA.com twins matched on `(game_date, home_team, away_team)`, then delete the orphaned copies, then add a guard index) — deferred deliberately; don't attempt it casually mid-season. The bad 2026-08-03 projection rows were healed in place (projected_games recomputed per player with clean 82-game denominators; max now 72), but the committed v1.3 Action will REGENERATE inflated values on its next daily run until the engine fix in the working tree is pushed.
