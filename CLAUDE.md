- **Settings modals must hydrate local state only AFTER their async source resolves, and never persist un-hydrated state.** The commissioner "Edit …" modals in [components/commissioner/](components/commissioner/) are always-mounted (`visible` toggled) and seed local `useState` in a `useEffect`. - Non-critical **post-response** work in edge functions — push fan-out (`notifyTeams`/`notifyLeague`), matview refreshes, best-effort logging — should be deferred off the response path with `deferWork(promise, label)` from [supabase/functions/_shared/background.ts](supabase/functions/_shared/background.ts). It wraps `EdgeRuntime.waitUntil` (keeps the worker alive until the promise settles) and falls back to an unawaited `.catch()` under `supabase functions serve`. `deferWork` catches + logs failures, so ONLY pass work whose failure is **non-fatal** to the request, and evaluate the promise's inputs BEFORE the call (they're captured when the promise is created). A Postgrest query builder is a thenable, not a real `Promise` — wrap it in an async IIFE: `deferWork((async () => { await supabase.rpc('…') })(), 'label')`. - Supabase realtime channel names for `postgres_changes` (and any non-shared `presence`) subscriptions created inside a `useEffect` MUST be built with `uniqueChannelTopic('base-name')` from [lib/supabase.ts](lib/supabase.ts). Plain deterministic names — and even `` `name-${Date.now()}` `` — collide when React re-fires effects within the same millisecond (notification tap, auth refresh, concurrent re-render, foreground transition) because `supabase.removeChannel()` is async. The old channel is still in `joined` state and `realtime.channel(topic)` returns it instead of creating a new one — the next `.on('postgres_changes', ...)` then throws `cannot add 'postgres_changes' callbacks ... after subscribe()` and Hermes can crash natively. `uniqueChannelTopic` combines `Date.now()` + a process-wide monotonic counter + `Math.random()` so collisions are impossible. Broadcast channels (e.g. `lottery:${leagueId}` in [app/lottery-room.tsx](app/lottery-room.tsx)) and SHARED presence channels (e.g. `chat_presence_${conversationId}` in [hooks/chat/useReadReceipts.ts](hooks/chat/useReadReceipts.ts)) are exempt — they need deterministic names so peers can match. - All edge functions return HTTP responses via [supabase/functions/_shared/http.ts](supabase/functions/_shared/http.ts) — do not hand-roll `new Response(JSON.stringify(...), { headers: ... })`. - All edge function input validation runs through [supabase/functions/_shared/validate.ts](supabase/functions/_shared/validate.ts), which re-exports Zod (`z`) and exports `parseBody(schema, body)`. Define `const Body = z.object({...})` at the top of `index.ts` immediately after the imports, then `const { ... } = parseBody(Body, await req.json())` in the handler. Validation failures throw `HttpError(400, "<path>: <message>")` so they route through `handleError` automatically — never hand-roll `if (!x) throw` for shape/type checks Zod can express. Things Zod handles natively (REMOVE the ad-hoc check): required (default), UUID (`z.string().uuid()`), string bounds (`z.string().min(N).max(M)`), number bounds (`z.number().int().min(M).max(N)`), enums (`z.enum([...])`), non-empty arrays (`z.array(...).min(1)`), optional (`.optional()`), ISO timestamps (`z.string().datetime()`), date strings (`z.string().regex(/^\d{4}-\d{2}-\d{2}$/)`), booleans. Preserve the **existing user-facing error message** when adding a Zod constraint by passing it as the second arg: `z.string().min(1, 'Question must be 1-500 characters')` — keeps client-side error strings stable. What stays inline (don't try to push to Zod): anything that depends on a DB-fetched value (cross-row checks, `closes_at > now()`, `selection_idx < options.length`), and auth/ownership checks. - New `SECURITY DEFINER` functions: Supabase's default privileges grant `EXECUTE` to **anon + authenticated** on every new `public` function, and `REVOKE … FROM public` does **not** strip those role-specific grants. A client-callable SD function therefore needs an explicit `REVOKE … FROM anon` (leaving `authenticated` + `service_role`, matching `transfer_team_ownership` / `increment_team_count`); an internal helper that has no auth check of its own and is only `PERFORM`ed by other SD functions needs `REVOKE … FROM anon, authenticated` so only the definer callers (running as owner) and `service_role` can reach it. **The converse also holds and is the trap that actually fires: `REVOKE … FROM anon, authenticated` does NOT strip the implicit `PUBLIC` grant, and `PUBLIC` covers anon** — so a function locked down that way is still callable by unauthenticated clients. Always pair the role revokes with `REVOKE EXECUTE ON FUNCTION … FROM PUBLIC`. **Verify with `has_function_privilege('anon', 'public.fn(argtypes)', 'EXECUTE')`, NOT `information_schema.role_routine_grants`** — that view only lists grants to named roles, so a `PUBLIC`-only grant is invisible in it and the function looks locked when it isn't. Precedent: the `lockdown_security_definer_grants*` migrations, and [20260727010000_revoke_public_execute_secdef.sql](supabase/migrations/20260727010000_revoke_public_execute_secdef.sql), which closed a live email-enumeration hole on `profile_id_for_email` that survived its own migration's `REVOKE … FROM anon, authenticated`.

- **"EAS updates aren't going through / the Install button never shows" is always a runtimeVersion mismatch, and it fails silently.** `app.json` sets `runtimeVersion: { policy: "fingerprint" }`, so a binary only accepts updates published under its OWN embedded fingerprint — publish under any other hash and `checkForUpdateAsync()` returns `isAvailable: false` with no error, no log, and no prompt from `OtaUpdateChecker`. Diagnose before touching anything: compare `npx eas build:list --limit 3` (`Runtime Version` of the installed build) against `npx eas channel:list` (the branch's most recent update group), then run `npx eas-cli@latest fingerprint:compare --build-id <build-id>` — it names the exact differing source. **The trap that keeps firing is that non-native files are fingerprint sources**: `.gitignore` (reason `bareGitIgnore`) orphaned build 103 on 2026-07-14 when a commit merely swapped a `!scripts/fonts/*.py` negation. [fingerprint.config.js](fingerprint.config.js) now sets `sourceSkips: ['GitIgnore']` to stop that specific one, but any new native dep, plugin, or `app.json` native key legitimately bumps the fingerprint and genuinely requires a rebuild. To rescue an already-orphaned build without rebuilding, republish the same JS under the shipped binary's hash: `EXPO_UPDATES_FINGERPRINT_OVERRIDE=<that build's runtimeVersion> npx eas update --branch production --platform ios --message "…"`. Only do that when `fingerprint:compare` shows the diff is cosmetic (a text/script/ignore-file edit) — if a real native module changed, the override ships JS against a binary that lacks it and you get the OTA-apply crash class. Must be run from a real terminal: `eas update` treats any non-TTY as `--non-interactive` and then demands `--environment`, which is the one flag that must NOT be used (it pulls EAS server-side env instead of letting Metro read `.env.local`).

- **An EAS *build* that dies at `CONFIGURE_EXPO_UPDATES` with "Runtime version calculated on local machine not equal to runtime version calculated during build" means local `node_modules` drifted from `package-lock.json` — run `npm ci`.** This is the build-time sibling of the OTA trap above and it looks nothing like a dependency problem: the working tree is clean, nothing native changed, and `eas fingerprint:compare --build-id <id>` reports a **match** — because it compares local against the fingerprint EAS *stored at submit time* (which IS the local one), not the hash the worker recomputed. The worker installs with `npm ci`; the local box fingerprints whatever is on disk. Since ~234 of the ~248 fingerprint sources are config-plugin files under `node_modules`, a stale tree moves the hash on its own (2026-07-21, build `b350517f`: an install from 07-06 vs a lock bumped to newer `expo` / `expo-sharing` / `expo-splash-screen` / `expo-modules-core` / `@xmldom/xmldom` / `uuid` / `plist` patches, which also shifted the plugin require graph). Tell-tale that it's the local side: EAS's hash equals the **previous successful build's** runtimeVersion. Verify the fix locally before spending another build — `require('@expo/fingerprint').createFingerprintAsync(process.cwd(), { platforms: ['ios'] })` must equal the "calculated on EAS" hash (pass `platforms` — an unscoped call hashes ios+android and yields a third, meaningless hash). To read the worker's hash and the exact per-source diff, fetch the build's `logFiles` from the EAS GraphQL API (`expo-session` header = `sessionSecret` in `~/.expo/state.json`); the line after `"Difference between local and EAS fingerprints:"` is a JSON array of `added`/`removed`/`changed` sources. Cheap smell test any time before building or publishing an update: `npm ls --depth=0` reporting `invalid`/`missing`, or `node_modules/.package-lock.json` older than `package-lock.json`.

- **PostgREST silently truncates any response at `max_rows` (1000) — including explicit `.limit()`s beyond it.** When batching an N+1 into a grouped `.in(...)` query (edge functions especially), a result set that scales with the id list WILL eventually cross 1000 rows and gets cut with NO error — downstream code then sees a partial map and quietly mis-computes (worst case: finalize-week scoring with partial weights would have committed wrong winners permanently). Either chunk the id list so the worst-case response stays well under 1000 (see `chunked()` in [supabase/functions/finalize-week/index.ts](supabase/functions/finalize-week/index.ts) — leagues: 500/req at 1 row each; scoring settings: 25/req at ≤30 rows each), or keep the query per-parent-id when each parent's rows are few (streaks). Related pgmq trap: `pgmq_read` increments `read_ct` and hides the message for the visibility timeout on EVERY read — never read a queue you might not process, or budget-skipped messages eventually dead-letter with zero invocation attempts.

- **The projections engine connects as the least-privilege `projections_engine` role — a new source table needs a GRANT *and* an RLS policy in the same commit as the Python change.** `PG_DSN` in the GitHub Actions projections workflows is NOT a full-privilege connection string; [20260603000001_projections_engine_role.sql](supabase/migrations/20260603000001_projections_engine_role.sql) created a NOLOGIN role scoped to exactly the tables the engine touched at the time (SELECT on `players`/`player_games`/`game_schedule`/`season_config`, INSERT/UPDATE/SELECT on `player_projections`, later `player_archetypes`/`player_props`). - **Season-projection model changes are decided by held-out backtest, never by reasoning — and the NBA pair is in-sample, so don't tune on it.** The 2026-08-02 audit built a lab harness that scores any variant on 5 genuine train→test pairs (WNBA 2020..k→k+1 for k=2021..2024, plus NBA 2024-25→2025-26) using per-game fantasy RMSE, season-TOTAL RMSE, and rank correlation. Two findings shipped as `franchise-v1.4`. (a) `experience_curve` is now **sport-gated via `SPORT_SEASON_PARAMS[sport]["experience_curve"]`** — OFF for WNBA, ON for NBA. Because `experience_seasons` clamps career length to 5, that curve has exactly two reachable outcomes (+10% at ≤2 seasons, 1.00 otherwise), so the flag really means "apply the young-player boost"; the boost is NBA-shaped and cost WNBA RMSE on 4/4 pairs (mean −0.175, paired Wilcoxon p=0.004) while removing it hurt NBA (+0.127). (b) `project_games_blended` (a 50/50 regression of the player's recency-weighted GP% toward the league mean) **replaces `project_games_played`'s shrink+injury+trend stack on the Franchise path** — the old model lost to the plain blend on season-total error, which is the draft board's view and the largest single term in it (58% of NBA total squared error); totals improved on 5/5 pairs (WNBA −18.9, NBA −8.9) and total rank correlation on 5/5. `project_games_played` and its `GP_SHRINKAGE`/`INJURY_*`/`TREND_*` constants **stay** in season_project.py because the standalone WNBA Excel script (`build_projections`) still calls it; only the Franchise runner switched, which is why `injury_penalty` is gone from `SPORT_SEASON_PARAMS`. Rules for the next model change: bump `MODEL_VERSION` (output values changed → model eras must stay segmentable); prove it on the WNBA pairs, since **`MPG_FULL_CONF_FRAC`/`RATE_FULL_CONF_FRAC` were themselves tuned on NBA 2024-25→2025-26, making every NBA head-to-head in-sample and biased pro-current**; and treat a single-pair RMSE delta under ~0.4 as noise (across-pair σ is 0.18–0.40) — require 4/4-or-5/5 sign consistency plus a pooled paired test. Settled negatives from the same audit, with revisit triggers: position/empirical-Bayes priors, per-team minute-budget rescaling, kNN/PECOTA comparables, and direct gradient boosting were all measured and all null-or-worse at this data depth (~1,100 WNBA + ~1,000 NBA player-seasons); revisit only once WNBA has ~2 more transition seasons AND `player_historical_stats` holds ≥2 archived NBA seasons. The known-largest remaining gap is **coverage, not accuracy**: candidates come from `fetch_active_players` (= played last season), so every rookie is unprojected — 15–20 of each WNBA season's actual top-100.

- **Historical game-log depth is a per-sport judgement, not a universal good — and `lookback_seasons` lives in `SPORT_SEASON_PARAMS`.** On 2026-08-03 the NBA history hole was closed by [backend/backfill_nba_game_logs.py](backend/backfill_nba_game_logs.py) (BDL `/v1/stats`, seasons 2019-2024: ~213k `player_games` rows, 1,237 games/season, 597 retired players created) and WNBA 2010-2019 by the existing [backfill_wnba_game_logs.py](backend/backfill_wnba_game_logs.py) (~47k rows). NBA went from 1 prior season to 5 in the engine's window — 2,608 player-seasons, **1,665 season-to-season transitions where there were 0**. The trap: the old blanket `lookback_seasons=5` had been *inert* for NBA (there was nothing to look back at), and the backfill made it live. Deep history turns out to help WNBA and **hurt** NBA — per-game RMSE vs training on last season alone: WNBA -0.340/-0.433/-0.377 at depths 2/3/4 (better on 3/3 test seasons) versus NBA +0.015/+0.053/+0.166 (worse on 2/3, 2/2, 1/1). Roster churn is the likely reason: a WNBA role from three years ago still describes the player, an NBA one is stale and dilutes last season through the `0.5^age` recency weights. So NBA is capped at 2 (1 vs 2 is a wash inside the ±0.4 noise bar; 2 keeps the extra `sample_games` evidence the shrinkage uses) and 3+ must not return without a fresh backtest. **Two rules when adding history for any sport: (1) re-run the depth sweep before assuming more is better — hold the test season fixed, vary training depth, and require a consistent sign across ≥3 test seasons; (2) backfilled players MUST be written with `pro_team = NULL`** — `pro_team IS NOT NULL` is the ONLY server-side gate keeping someone out of the free-agent list, draft board, autodraft, commissioner add and rankings (nothing filters on `status`), and those queries order by `avg_pts desc` without `nullsFirst: false`, so Postgres sorts NULLS FIRST and a statless retiree lands at the TOP of the list and eats the 200/600/1000-row cap. The WNBA script used to set the player's last historical team plus `status='active'` — exactly that shape — and only the daily `sync-players` sweep (which NULLs `pro_team` for any `external_id_bdl` absent from BDL's active list) kept it invisible; both scripts now write `status='retired'` and no `pro_team`. Separately, the backfill's real measured win for NBA was **fidelity, not depth**: replacing the 1-dp rounded `player_historical_stats` averages for 2024-25 with true game logs moved the same train/test pair from 7.043 to 6.891 RMSE.

- **The NBA season model is franchise-v1.5: per-sport recency decay, per-sport shrink ramps, and a dedicated minutes model — every constant in `SPORT_SEASON_PARAMS` is backtest-validated, so changing one requires re-running the lab protocol, not a hunch.** The 2026-08-03 accuracy round ran on 5 native NBA train→test pairs (possible only after the game-log backfill), with hyperparameter tuning restricted to tests 2021-2023 and **2024/2025 as untouched holdout**; believability bar = consistent sign on ≥4/5 pairs plus pooled paired Wilcoxon (single-pair RMSE deltas under ~0.4 are noise). The shipped stack (NBA only; WNBA numerically unchanged): (a) `recency_decay 0.3` — season t-2 gets weight 0.3 not 0.5, roles go stale; (b) shrink ramps `0.55/0.35` (the old 0.40/0.25 were tuned on the then-only 2024→2025 pair, which is now flagged in-sample); (c) [projections/minutes_model.py](projections/minutes_model.py) — ridge (alpha 10) over native season→season+1 transitions with depth-chart features (`min_rank`, `team_min_share`, box-score `usg_pct`), predictions blended 50/50 into engine minutes via `blend_into_projection` (rates untouched, only opportunity moves; falls back to engine minutes when a player lacks team/features or transitions < 300). The oracle ceiling for honesty: actual-minutes knowledge would cut RMSE ~in half; the whole stack recovers ~10% of that gap — the rest is in-season information (injuries, trades, rotations) that box-score history cannot see.

- **Rookies are projected by DRAFT-SLOT priors (franchise-v1.6) — `players.draft_round`/`draft_number` feed [projections/rookie_priors.py](projections/rookie_priors.py), and the columns have a one-way write contract.** Before this, season-snapshot candidates were "played last season", so every incoming rookie was absent from `player_projections` entirely (invisible on draft boards and the FA wire). The three keys are `rosterInfo` ([useTeamRosterInfo](hooks/useTeamRosterInfo.ts) — PlayerDetailModal's add/IR/taxi gates), `freeAgentRosterInfo` ([useFreeAgentRosterInfo](hooks/useFreeAgentRosterInfo.ts) — FreeAgentList's `rosterIsFull` + open-slot counter), and `leagueOwnership` (its `roster_slot` column feeds `useRosterNeeds`' position chips). Two hooks computing the same count from the same rows under different keys is the root hazard; until they're merged, route every invalidation through `invalidateRosterCounts(queryClient, leagueId)` in [utils/roster/rosterCounts.ts](utils/roster/rosterCounts.ts). It is deliberately league-scoped, not team-scoped — `['rosterInfo', leagueId]` prefix-matches every team, which is exact for the acting user (one team per league) and is also usable from the realtime fan-out, which learns that a `league_players` row changed without learning whose it was. **Two layers must both carry it:** the direct action path (roster.tsx's IR/TAXI move, FreeAgentList + PlayerDetailModal add/drop, [useTradeDetailActions](hooks/useTradeDetailActions.ts)' shared `invalidate()`), and [useRosterChanges](hooks/useRosterChanges.ts)' `flush()` — the latter is the ONLY path that reaches a roster change made on **another device** (the counter-party to a trade, a cron-processed waiver, a commissioner action), and it had the same gap. Prefer adding to an existing shared `invalidate()` over per-branch precision: over-invalidating an inactive query only marks it stale, whereas missing one is a 5-minute phantom bug. This is a *client-perception* class only — `assert_can_add_free_agent` is the real enforcement, and a stale cache can only block a legal add, never permit an illegal one.

- **Anything that rebuilds the draft board must re-draw the slot order in the same transaction — an unowned board starts, and a started unowned draft can't be walked back.** `draft_picks` rows carry the order in `current_team_id`/`original_team_id`, and `replace_draft_picks` (the league-resize path in [EditBasicsModal](components/commissioner/EditBasicsModal.tsx)) DELETEs every pick and re-inserts them NULL. The draw used to run *only* on member join (`app/create-team.tsx` → `assign_initial_draft_slots`, gated on `team_count >= leagues.teams`), so the classic case — a 12-team league where 8 people showed up, shrunk to 8 so it's finally "full" — passed the fill gate at a moment nothing was watching and left every pick unowned. Scheduling succeeded, `start-draft` succeeded, and the draft opened with nobody on the clock (live casualty: league `McQuade`, 26/26 picks unowned, `status='in_progress'`). The draw now lives in the internal `draw_initial_draft_slots(league_id)` helper ([20260804140000_redraw_draft_slots_on_resize.sql](supabase/migrations/20260804140000_redraw_draft_slots_on_resize.sql)); `assign_initial_draft_slots` is a thin membership-checked wrapper over it, `replace_draft_picks` `PERFORM`s it after the rebuild, and [start-draft](supabase/functions/start-draft/index.ts) refuses (409) to flip `pending→in_progress` when no team owns the current pick, retrying the draw once first. Rules: the helper is SD with **no auth check** — keep it revoked from `PUBLIC`/`anon`/`authenticated` and call it only from another SD function or service_role (`replace_draft_picks` is granted to service_role, where `is_league_member` is always false — that's why the wrapper couldn't just be reused). It deliberately no-ops on manual order, on any non-null `offseason_step` (a lottery / `create_season_draft_atomic` order is deliberate), and once a pick has `selected_at`. **A manual order cannot be re-drawn** — the resize clears it and the commissioner must re-set it, so invalidate `draftSlotsAssigned`/`draftLobbyOrder` after a rebuild or the home hero's 5-minute-stale `true` lets them schedule against a wiped board. Known, unfixed limitation of resizing: it also destroys any **traded** startup/future picks, since every row is re-inserted from scratch.

- **Any surface that RANKS or SORTS the shared player pool has to switch basis pre-tipoff, and an all-zero pool must render "no rank", not a pool of co-leaders.** `player_season_stats` is scoped to `season_config.is_current`, so from the rollover until tipoff (~11 weeks for NBA) every player reads `games_played=0, avg_*=null` and scores 0.00 fpts. Ranking that pool gives *everyone* the same score, and standard competition ranking then renders `#1 OVR` + `#1 PG` on all 585 NBA players — which is what the player-detail header shipped (user-reported 2026-08-04). This is the third instance of the same class after the roster stat window and the `SeasonAverages` season chip, so treat it as a standing rule: `computeRankings` ([utils/scoring/playerRankings.ts](utils/scoring/playerRankings.ts)) takes an optional season-horizon projection map and ranks on projected FPTS/G when given one, carries the choice back out on `PlayerRanking.basis` (`'season' | 'projected'`), and **returns an empty map when the top score is ≤ 0** — that guard is what keeps NFL (no projections engine) from re-showing the all-#1 pool rather than nothing. [usePlayerRankingsMap](hooks/usePlayerRankings.ts) owns the calendar decision (`isSeasonStarted` + `getSportToday`) and is consumed by BOTH the detail badges and [useCompareData](hooks/useCompareData.ts)'s Rankings rows so the two can't disagree about the basis; it re-uses the `(sport,'season')` projection query key the modal already fetches, so it costs no extra request. **A projected rank must be labelled** — [PlayerRankBadges](components/player/PlayerRankBadges.tsx) puts a `PROJECTED` caption above the pills and says "Projected ranking" in its a11y label, same reason the pre-season averages chip reads `'27 PROJ`. Two ceilings to know before leaning harder on this: `usePlayerSeasonStats` caps the pool at 600 rows ordered by `avg_pts` — pre-tipoff every value is NULL so the ordering is arbitrary and a pool over 600 (NFL is 995; NBA is 585 but camp rosters could cross it) drops players silently, and they get no badge at all; and `usePlayerProjections` doesn't paginate, so it inherits the PostgREST 1000-row cap (NBA is at 630 for 2026-27).

- **Prospect consensus merges on a SUFFIX-STRIPPED slug, and `prospect_rankings` orphans are never auto-deleted.** Ranking sources disagree on generational suffixes — on 2026-08-03 NBADraft.net started printing "Darius Acuff" where RotoBaller prints "Darius Acuff Jr.", which minted a SECOND board row. `buildConsensus` charges a missing source `list length + 10`, so one player split into two half-ranked entries and Acuff fell from #7 to #35 and #57 (7 players hit: Acuff, Mikel Brown, Morez Johnson, Christian Anderson, Tarris Reed, Chris Cenac, Jaron Pierre). The fix is `canonicalSlug()` in [prospect-rankings/src/lib/names.js](prospect-rankings/src/lib/names.js), used as the merge key in [consensus.js](prospect-rankings/src/consensus.js), keeping the LONGER slug/name for display. Three things to know when touching this: (a) **the surviving slug must stay the one `players.player_slug` and the Contentful entry already use** — the app joins the board to Contentful and to `players` on that slug ([useProspects](hooks/useProspects.ts), [useProspectConsensus](hooks/useProspectConsensus.ts)), so picking the other form silently unranks the player; "longer wins" happens to be right today because every affected pair is `-jr` vs bare, but verify against `players` before trusting it. (b) **A wrong merge can only fire where 2+ sources cover the same draft year** — today that is ONLY 2026 (nbadraft + rotoballer); 2027 is tankathon alone and 2028-30 are one ESPN SC Next list each. Adding a second source to any of those years makes same-name-different-person collisions newly possible. (c) **[sync-supabase.js](prospect-rankings/src/sync-supabase.js) only upserts — it never deletes**, deliberately (a player who falls off all boards keeps their last row). So a slug-form change leaves an orphan row at a stale rank forever, and `sync-contentful` will also have created a duplicate unpublished draft entry for it; both need manual cleanup, and the orphan is invisible until someone publishes that CMS draft. Also delete the broken run's `rank_history` rows before re-running or the corrected board shows a fake ▲ spike (the `prospect_board` view diffs against the previous snapshot).

- **ESPN blocks this pipeline's IP-sensitive endpoints differently from a laptop vs. GitHub Actions — check WHERE it's failing before "fixing" it.** `prospect-rankings/src/lib/http.js` routes HTML page fetches through the [scrape-proxy](supabase/functions/scrape-proxy/index.ts) edge function when `SCRAPE_PROXY_URL` is set, because runner IPs are on Cloudflare/Akamai deny lists (nbadraft 403s, espn.com serves a table-less challenge page that reads as an empty board). But [src/lib/espn.js](prospect-rankings/src/lib/espn.js) uses its OWN raw `fetch` and does NOT go through the proxy — and `site.api.espn.com` 403s from a normal residential IP while working fine from Actions. That's the exact inverse of the HTML case. Consequence: a local `npm run scrape` writes correct rankings but silently no-ops the ESPN-dependent steps (`stats.js` roster resolution, `enrich.js` field backfill, `sync-headshots.js`), logging "no ESPN roster for kansas" for obviously-real programs. Don't read that as a code bug. To verify which side is blocked, `curl` the roster endpoint directly and compare against `player_ids.resolved_at` (ids DID resolve on the last CI run ⇒ Actions is fine). Run the pipeline from Actions, not locally, whenever the ESPN steps matter.

- **`prospect-rankings/sql/schema.sql` is APPLIED and its RLS policies are looser than production — do not re-run it.** The vendored file creates `public read rankings` / `public read history` policies with `using (true)`, but the live policies on `prospect_rankings`/`rank_history` are `auth.role() = 'authenticated'`. The file's `drop policy if exists` names don't match the live policy names, so re-running would ADD the permissive policies alongside (policies are OR'd) and open the board to anon. The tables already exist; there is no reason to run it again.

- **The blocked-language filter matches WHOLE WORDS only — never substring-match a de-spaced blob, and remember the SQL trigger is the real enforcer.** Moderation runs in three places off one word list: [utils/moderation.ts](utils/moderation.ts) (client pre-check, nicer error before the round trip), [_shared/moderate.ts](supabase/functions/_shared/moderate.ts) (`checkWordList` + a Claude Haiku pass, used only by the `moderate-messages` cron), and the `check_blocked_content()` plpgsql trigger — attached to `chat_messages`, `teams`, `leagues`, `commissioner_announcements`, `commissioner_polls`, `commissioner_surveys`, `survey_questions` — which is what actually rejects the insert. The client and the trigger each ran a third pass that stripped EVERY space and substring-matched with no word boundaries, to catch slurs split as `f a g` / `n igger`. That flags any two innocent words whose join straddles a slur, and because the poll/survey modals concatenate *every field* (`[title, description, ...prompts, ...options].join(' ')`) before checking, each field boundary was another chance to collide. Live casualty (2026-08-06, league `NBA Dynasty 🏀`): a commissioner could not post an offseason survey because "supports **pick**s" and "1.5 hour**s/pic**k" both contain `spic`. Same class: `suspicious`/`suspicion` → spic, `raccoon`/`tycoon` → coon, "half a game" → fag, "Chicago okay" → gook. The fix ([20260807120000_fix_blocked_content_false_positives.sql](supabase/migrations/20260807120000_fix_blocked_content_false_positives.sql) + `containsSplitBlockedWord`) joins runs of **adjacent whole words** and requires the join to **equal** a blocked word exactly — splitting a slur always yields whole fragments, so nothing the old pass caught is lost. Known accepted residual: "go ok" still joins to `gook`; for a moderation filter that's the right side to err on, and it's not systematic the way ordinary vocabulary was. Rules: the SQL `blocked_words` array is hand-mirrored from `SPLITTABLE_WORDS` and gated by a text-parsing parity test in [__tests__/moderation.test.ts](__tests__/moderation.test.ts) — change both in one commit; only pure-alpha terms belong in the split list (a phrase can't equal a space-free join, and `1488` can't survive `normalize()`, which maps 1→i and 4→a); and the `chat_messages` rapid-fire branch stays a substring match on purpose, since it only concatenates messages of ≤3 chars where the fragments ARE the evasion. **A client-side fix does not unblock anyone on its own** — the client check returns early before the mutation, so it needs an OTA, while the trigger fix is live the moment the migration lands. Second bug found in the same function and fixed alongside: the options loops guarded on `(new_json->'options') IS NOT NULL`, but `to_jsonb()` renders a NULL column as the jsonb scalar `null`, which passes that guard and makes `jsonb_array_elements_text` raise `22023: cannot extract elements from a scalar` — `survey_questions.options` is NULL for every `free_text` and `rating` question, so any survey containing one died with a raw 500. Guard jsonb array iteration with `jsonb_typeof(x) = 'array'`, never `IS NOT NULL`.

- **`sync-headshots.js` is deliberately NOT wired into the weekly prospect run.** It re-hosts ESPN/Getty-licensed images into our own Contentful assets, so Noah's `run.js` call was removed when the Aug 2026 drop was vendored; it lives on as `npm run headshots` (supports `--dry-run` and `--limit N`). Filling a few hundred blank photos is a licensing decision to make deliberately, not a cron side effect. If it's ever promoted back into `run.js`, that's a product/legal call, not a cleanup.
